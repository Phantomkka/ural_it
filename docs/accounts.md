# NETCITY ID

Логин (без учёта регистра) и пароль работают на разных устройствах. При регистрации игрок явно выбирает привязку текущего гостя или новый пустой профиль и подтверждает последствия. Вход в существующий аккаунт не складывает два баланса; непривязанный гость остаётся в браузере.

Привязка меняет владельца существующего `profile_id`, не копирует игровые данные. NET, XP, инвентарь, задания, диагностика, клиентские заявки, операции и журнал наград остаются на месте. Уникальные ограничения аккаунта/профиля и блокировка строки в одной транзакции защищают от повторной и конкурентной привязки. Старый гостевой ключ отзывается; его открытые игровые соединения закрываются. Ошибка после создания аккаунта требует повторного входа, а не повторного переноса.

Пароли: встроенный асинхронный scrypt, N=131072, r=8, p=1, случайная соль 128 бит, ключ 256 бит. Одновременно работают не более двух вычислений; пароль ограничен 12–128 символами / 512 байтами. Параметры соответствуют варианту scrypt из [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Новых зависимостей нет.

Сессия — случайный 256-битный секрет, в БД только SHA-256. Срок — 7 дней, новый вход создаёт новый секрет. Production cookie `__Host-netcity_session`: Secure, HttpOnly, SameSite=Strict, Path=/, без Domain; локальный HTTP использует отдельное имя. Cookie и пароль не записываются в localStorage/sessionStorage. В браузере остаётся только несекретный признак ранее использованного аккаунта, чтобы истёкшая сессия не заменялась гостем молча. Рекомендации: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

POST требует точный Origin, JSON и CSRF-заголовок, связанный HMAC с HttpOnly session/preauth cookie. Auth-ответы не кэшируются, CORS для них закрыт. Matchmaking аккаунта также проверяет Origin и серверную сессию; `profileId` из клиента не используется. Выход отзывает текущую сессию, а восстановление — все сессии. Действия с прогрессом повторно проверяют полномочия; пассивные подключения других процессов перепроверяются каждые 10 секунд.

Лимиты сохраняются в PostgreSQL: 30 попыток с IP и 8 на логин за 15 минут, включая успешные операции. Возвращается Retry-After; неизвестный логин проходит такое же вычисление хеша. За доверенным единственным reverse proxy используется `AUTH_PROXY_HOPS=1` (задан в шаблоне Compose); прямой сервер по умолчанию не доверяет X-Forwarded-For. `NETCITY_ORIGIN` при необходимости фиксирует точный внешний origin; production допускает только HTTPS. Серверный порт в существующей схеме остаётся внутренним.

Почтового сброса нет. При регистрации выдаётся случайный одноразовый ключ восстановления: сохраните его в менеджере паролей. На сервере только его хеш. Ключ меняет пароль, отзывает сессии и заменяется новым ключом. Повторное использование старого ключа запрещено. Без пароля и сохранённого ключа автоматическое восстановление невозможно; доступ не выдаётся по одному никнейму или сообщению в поддержку.

Миграция 004 добавляет accounts, account_sessions и auth_buckets, не удаляя игровые таблицы. Проверяется повторный запуск миграций, сохранение профиля и сессии после перезапуска пула. Без PostgreSQL UI явно помечает аккаунты как временные. Рабочая БД и production не обновлялись.

Совместимость: приложение из PR #20 не умеет входить в аккаунты. После привязок откат к нему сохранит данные, но заблокирует вход привязанных игроков до возврата версии с аккаунтами. Не восстанавливайте автоматически отозванные гостевые ключи и не удаляйте таблицы аккаунтов.

Целевые команды: `node --import tsx --test apps/server/src/auth.test.ts`; `TEST_DATABASE_URL` + `apps/server/src/auth.postgres.integration.ts`; Playwright `tests/accounts.spec.ts`, `tests/identity.spec.ts`, `tests/reconnect.spec.ts`. Полная регрессия не подменяется этими проверками.
