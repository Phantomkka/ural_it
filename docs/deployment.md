# NETCITY ONLINE: изолированное развёртывание

Требования: Ubuntu 22.04/24.04+, Docker Engine и Compose v2.20+, Bash, Git; ориентир — минимум 2 vCPU, 2 ГБ свободной RAM и 10 ГБ диска. Это ориентир, не замена проверке нагрузки других приложений. Сначала проверить `deploy/audit.py`: он читает ресурсы, порты, Docker и имена доменов, не выводя env/пароли контейнеров и полные конфиги proxy. Каталог приложения, project name, порты и лимиты выбрать по фактическому состоянию сервера.

**Перед изменением существующих DNS, firewall или работающего reverse proxy требуется отдельное подтверждение пользователя с конкретным планом.** Не останавливать чужие приложения, не выполнять Docker prune, `down -v`, reset --hard или удаление чужих каталогов. Не подключать этот стек к существующей БД: для него отдельные сеть, secret и volume.

## Состав

- `Dockerfile`, target `client`: собранные Vite-файлы и Caddy; dev Vite в production не используется.
- Target `server`: Node 24, только runtime-зависимости сервера, непривилегированный процесс, read-only filesystem. Учтены вложенные npm workspace-зависимости.
- `migrate`: тот же образ, одноразовая миграция; игровой сервер ждёт её успеха и готовности БД.
- PostgreSQL 16: постоянный volume, только внутренняя сеть; **нет ports**.
- Colyseus: только внутренняя сеть; **нет ports**.
- Caddy: единственная точка входа; HTTPS, `/game/*` → Colyseus с WebSocket Upgrade; постоянные сертификаты в отдельном volume. Административный интерфейс отключён. Внутренний healthcheck не опубликован.
- Отдельные Docker project/network/volumes/images, restart policies, ограничения CPU/RAM/PID и ротация логов. Новые версии не используют чужие имена контейнеров или external networks. Базовые multi-architecture образы закреплены digest; список — `deploy/images.lock.json`.

## Первый запуск в новом отдельном каталоге

Сначала убедиться, что целевой каталог не занят. Clone не должен перезаписывать существующие файлы:

```sh
git clone --branch feat/netcity-004-production https://github.com/Phantomkka/ural_it.git netcity-online
cd netcity-online
bash deploy/init.sh
```

`init.sh` создаёт новый `deploy/local` с правами 0700, случайный пароль и `.env` с правами 0600. Уже существующий каталог не переиспользуется и пароль никогда не заменяется. Можно передать новый абсолютный каталог вне checkout: `bash deploy/init.sh /path/to/new/shared-config`. В этом случае во всех командах задать `NETCITY_ENV_FILE=/path/to/new/shared-config/.env`. Пароль не выводится и не хранится в env Docker-контейнеров: используется secret-файл. Он остаётся доступен только пользователю развёртывания и нужным контейнерам.

Отредактировать `.env` по `deploy/.env.example` **без публикации пароля**:

- Для проверки только на сервере оставить `NETCITY_BIND=127.0.0.1`, порты 18080/18443.
- Если подтверждённый домен уже направлен на сервер и 80/443 свободны: `NETCITY_SITE=game.example.com`, `NETCITY_BIND=0.0.0.0`, `NETCITY_HTTP_PORT=80`, `NETCITY_HTTPS_PORT=443`. Caddy автоматически получает и обновляет публичный сертификат. Это сработает только при доступных извне challenge-портах и корректном DNS.
- Если 80/443 заняты работающим proxy, оставить loopback-порт 18080 и `NETCITY_SITE=:80`. Подготовить отдельный host route существующего proxy к этому порту, сохранить Upgrade/WSS и сначала согласовать изменение. TLS в этом варианте заканчивается на существующем proxy.
- Без домена первичный HTTP-тест: `NETCITY_SITE=:80`, разрешённый свободный HTTP-порт и публичный IP. Это **не означает готовый доверенный HTTPS**; для него нужен согласованный домен/сертификат. Не выдавать `localhost` CA за публичный сертификат.
- `NETCITY_PROJECT_NAME` должен быть новым, `NETCITY_UID/GID` — владельцем secret-файла; лимиты памяти подбирать по свободной RAM. В контейнер передаются только пути secret, не пароль в URL.

```sh
export NETCITY_RELEASE="$(git rev-parse HEAD)"
bash deploy/manage.sh config
bash deploy/manage.sh up
bash deploy/manage.sh status
```

При внешнем env-файле добавить `NETCITY_ENV_FILE=/absolute/path/.env`. При отсутствии Docker socket access команды Docker выполнить через разрешённый sudo; не менять группы/права других пользователей автоматически. Для Cloud-build с перехватывающим TLS-прокси задать `NETCITY_BUILD_CA` на предоставленный CA-файл: он используется только как BuildKit secret, не копируется в образ. На обычном VPS этого не требуется. Проверка TLS никогда не отключается.

При первом старте БД создаёт свой volume, затем миграция выполняется под advisory lock. При неудаче миграции или недоступной БД сервер не запускается. Production-bootstrap требует secret и не допускает временный режим. `manage.sh stop` останавливает только этот project, не удаляя данные.

Проверки:

```sh
curl --fail https://game.example.com/version.json
curl --fail https://game.example.com/game/health
# Оба ответа должны показывать тот же NETCITY_RELEASE, persistence — postgres.
```

Для `localhost` Caddy использует локальный CA только для лабораторного теста. Корневой публичный сертификат можно получить из своего Caddy-контейнера и передать в `curl --cacert` / `NODE_EXTRA_CA_CERTS`; не копировать ключи CA и не отключать проверку сертификата. В публичном браузере нужен доверенный публичный сертификат.

## Проверка клиента, мультиплеера и сохранения

С рабочей машины с Node/npm и checkout:

```sh
npm ci
NETCITY_URL=https://game.example.com npm run test:production
NETCITY_URL=https://game.example.com NETCITY_PROOF_FILE=/secure/new-proof.json npm run test:deployment
```

Browser-smoke загружает production-HTML/GLB, подключает двух гостей и проверяет UI снабжения через proxy, без dev-модулей. CLI-smoke перемещает двух реальных клиентов обычными игровыми сообщениями, проходит ремонт, получает NET/XP, покупает патч-корд и проверяет повторы и приватность. Proof содержит гостевой bearer-токен тестового игрока; файл создаётся исключительно новым с правами 0600. Не публиковать его и не коммитить.

После подтверждённого ремонтного окна на собственном стеке:

```sh
bash deploy/manage.sh restart-server
NETCITY_URL=https://game.example.com node deploy/smoke.mjs --verify /secure/new-proof.json
```

Проверяются баланс, XP, инвентарь и повтор прежней покупки без нового списания. В локальной проверке также перезапускалась сама PostgreSQL. Перезапуски игрового сервера отключают игроков; подключиться снова можно кнопкой HUD, токен остаётся во вкладке. Мир и позиции временные, профиль — в PostgreSQL. Смена origin (IP/HTTP → домен/HTTPS) может создать нового гостя: полноценного переноса/восстановления аккаунта нет.

## Обновление из GitHub и резервная копия

```sh
bash deploy/manage.sh backup
# Убедиться, что нет собственных незакоммиченных изменений. Ничего не удалять.
git status --short
git fetch origin feat/netcity-004-production
git switch --detach FETCH_HEAD
export NETCITY_RELEASE="$(git rev-parse HEAD)"
bash deploy/manage.sh up
bash deploy/manage.sh status
```

После отдельного одобренного слияния интеграции можно использовать `main` вместо feature-ветки. Никогда не делать force push/reset --hard ради обновления. У каждого релиза отдельный tag образа с SHA; volume и secret сохраняются. Сначала успешно собираются образы, затем выполняется миграция и запуск. Профили при этом остаются в БД. Восстановление dump/откат миграции — отдельная операция с согласованием, не автоматическая разрушительная команда обновления.

`manage.sh backup` создаёт custom-format pg_dump с правами 0600 в `deploy/backups` (либо `NETCITY_BACKUP_DIR`). Хранить защищённую копию отдельно от сервера. Команда не удаляет старые backup и не меняет данные БД. `manage.sh logs` выводит только последние 100 строк, пароли/токены приложение не логирует.
